How I Set Up Claude

02-120 Programming for Scientists, Fall 2026 · Phillip Compeau

This page is about the Claude stack that I have built to help me with my work: teaching, research, running courses, and everything in between. It is also about how you can build one of your own to help you in college, in this class and far beyond it.

Out of the box, Claude starts every conversation with amnesia. Almost everything in my setup exists to fix that. I give Claude a memory, standing rules, and skills it can reuse, and then I stay the manager. Several of these pieces are ideas you have already met in this course. You do not need all of this for your project, and the boxes at the bottom say which parts you need now and which are worth growing into.

1. Everything happens in Claude Code, in a folder

I spend most of my working day in Claude Code, using the strongest model available (right now, Opus 5.5). Every project is one folder, and every folder is a GitHub repository. Claude works on the files in that folder directly, so nothing gets lost in a chat window, and everything it builds is mine to keep, change, and share.

2. Claude gets a memory that I can read

A file called CLAUDE.md at the top of a folder is read at the start of every session. Mine says who I am, how I like to work, and where everything else lives. Behind it sits a folder of short notes, one topic per note, with an index that points to them. The index works like the dictionaries from Chapter 1: look up a topic, and get back the note about it. I keep the index short, and when something changes, I update the value for that key rather than adding a second entry next to it; otherwise the memory fills up with contradictions. Claude writes most of these notes, and I prune them.

3. I write my rules down once

Anything I got tired of repeating became a standing rule in memory: how I write, how I like my Python (type hints everywhere), and to commit and push when a job is done. If you correct Claude about the same thing twice, write it down.

4. Repeated work becomes a skill

Since Chapter 0, whenever we have found ourselves writing the same code twice, we have pulled it out into a function and called that function instead. Skills are the same idea for Claude: a skill is a short file of instructions for a task that I do over and over, which Claude loads when the task calls for it. I have skills for grading, building a syllabus, running course websites, and more. Two of them come from the Vibe Coding Studio and are made for students: learn-with-ai-tutor, which turns Claude into a tutor that teaches one idea at a time and quizzes you, and test-every-function, which makes Claude prove that each function works and explain the tests in plain English.

5. One brain across machines

My memory and skills live in a private GitHub repository that both of my computers point to, so Claude knows the same things wherever I sit down. It is the same clone, commit, and pull rhythm that you use with the course repository every week, and Git also gives me a history of every change to Claude's memory.

6. Claude works with the tools I use

Connectors let Claude work directly with other apps I use every day. I decide what it can touch, and anything that leaves my hands comes back to me for approval first. For your project, you need only GitHub and a place to deploy your app.

7. Secrets stay out of the chat

Passwords and API keys live in a password manager, and Claude reads them only when a command needs them. Never paste a key into a prompt, and never commit one to a repository.

8. I talk more than I type

I dictate most of my prompts with a speech-to-text app. Talking gets far more context out of my head than typing does, and context is what Claude needs most.

9. I stay the manager

Google studied what makes its best managers good (Project Oxygen), and most of what it found applies to managing AI. Here is what I do for the qualities that matter most.

  • A clear vision. I always start with the end in mind: what I am building, and what done looks like. I am never just chatting back and forth with my new AI friend. For anything bigger than a small fix, I start in plan mode and read the plan before any code gets written. This is the top-down programming of Chapter 3: agree on the highest-level function and the subroutines it needs before writing any of them.
  • Results oriented. Done means proven. I make Claude show that the result works, with the kind of tests you wrote in the Testing and Debugging recitation, an explanation in plain English, and a figure when one helps.
  • A good communicator. I say what I want and why, with all the context I have. In plan mode, I let Claude ask me questions before it builds anything.
  • Does not micromanage. I hand Claude a whole job rather than one line at a time. I check what the program does rather than reading every line, and I ask Claude to explain any code that I do not understand.
  • A good coach. I do not accept the first thing that comes back. I push back, ask why, and go another round; when I correct the same thing twice, it goes into memory so that it sticks.
  • A strong decision maker. When Claude surfaces a design choice, I make the call instead of letting it drift. I own every commit, which means I own every mistake in it.
  • Technical skills. I know enough to tell when something is off. That is why you are learning to program in this course, even though Claude can write the code.

10. Your stack and your project

Your own setup and your project submission live in different places, so you can build the first without giving it away in the second. Claude Code keeps a separate log for each folder that you work in, and your build journal is only the logs from your project folder, together with its Git history.

  • Do all of your project work in Claude Code, inside your project repository. Work that happens in a chat window or in another folder never reaches your journal, so we cannot give you credit for it.
  • Your personal memory and skills, which live in the .claude folder in your home directory, are never collected. Use them freely.
  • The CLAUDE.md and skills inside your project repository are part of your project and are submitted with it, so keep anything private out of them.
  • Folders for your other classes are yours alone; nothing from them is collected.
  • Before you push, you can read your journal/ folder and redact anything personal. Set up your build journal here.

What you need for your project

  1. Claude Code, working inside your one project repository on GitHub.
  2. A CLAUDE.md in that repository that says who you are, how you like to learn, and what you are building.
  3. The two skills above, added to your repository's .claude/skills/ folder.
  4. Your paper, sources, and data in the repository, so that Claude can teach them to you.
  5. The manager habits in item 9, from your first session to your last.
  6. Every project session in Claude Code, inside that repository (item 10).

Growing it through college

  1. Keep one folder per class, each with its own CLAUDE.md that says what the class is and how you want to learn it.
  2. When you study for any course, have Claude teach you one idea at a time and quiz you, rather than hand you answers.
  3. Each time you correct Claude about the same thing twice, add a line to memory; each time you do the same task three times, turn it into a skill.
  4. Put your memory and skills in a private GitHub repository, so that your stack grows with you from year to year.
